Pipeline freshness

Why customers ask this: "is my materialization/derivation caught up?" is the single most common OpenMetrics question — teams compare *_last_source_published_at_time_seconds against the current time to catch silent lag before a destination goes stale.

Thresholds shown (<5m good, 5m–1h delayed, >1h critical) are starting points, not Estuary defaults — tune them to your own SLA. Note this measures reporting latency: if the metrics pipeline itself is delayed, a task can look stale while data is actually flowing.

Data moved this month

Why customers ask this: "how many bytes have moved, and is the backfill done?" Byte/doc counters answer both — compare captured vs. materialized totals per task to spot a backfill still catching up.

Counters are cumulative month-to-date and reset at the start of each calendar month — to measure a shorter window, snapshot this endpoint twice and diff the values (or let Prometheus's rate() do it for you).

Errors & warnings by task

Why customers ask this: alerting on raw error counts. One real caveat worth knowing: logged_failures_total can include non-actionable failures like inferred-schema violations — pair it with Estuary's built-in shard-failure alerts (which only fire on repeated failures of the same build) rather than alerting on the raw count alone.

Busiest collections

Why customers ask this: the Collections page in the dashboard can't sort by volume across all collections and its CSV export is page-limited. These counters give you the same numbers, unbounded, sortable however you like.
